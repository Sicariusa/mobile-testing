# Perception Engine — Full-Repository Audit

> Adversarially-verified audit of the `mobile-testing` Android UI test runner. Six dimension auditors read the source in full and fanned out; every substantive finding was handed to an independent skeptic instructed to refute it by default and reproduce the failure in code. Only survivors appear here.

**Date:** 2026-09-16 · **Scope:** ~6,900 LOC (engine + cli + webapp + tests) · **Method:** multi-agent workflow, refute-by-default verification

**Interactive report:** [`docs/audit/perception-engine-audit.html`](perception-engine-audit.html) (open in a browser) · also published as a Claude artifact.

## Verdict

| Health | Findings | High | Medium | Low | Refuted |

## Executive read

mobile-testing is a thoughtfully architected perception-first QA runner whose core promise — a trustworthy PASS/FAIL — is undermined by a small set of specific, high-impact defects rather than pervasive rot. The most serious is that both perception channels grade text with case-folded substring containment (validator._hierarchy_has_text and ocr.ocr_find), so a genuine functional failure can read as PASS and correct software as FAIL; a silent long_click->tap degradation and an always-FAIL element_exists+value variant compound the false-verdict risk. Its stdlib web control panel is an unauthenticated, cross-site-drivable surface that interpolates an untrusted package into a device shell and joins user paths without confinement, exposing device-shell command execution, arbitrary-file read, and arbitrary-APK install. Durability is also at risk: same-second runs overwrite each other's evidence directory and screen-library writes are non-atomic and swallow errors, so the very artifacts the tool exists to produce can vanish silently. Offsetting this, the architecture (dual-channel perception plus a recovery ladder), the memoization and evidence scaffolding, and a FakeDevice pytest suite are genuine strengths, and adversarial verification refuted many candidate issues — the core logic largely held up. The defects concentrate in text-matching semantics, the web surface, persistence durability, and test coverage that gives false confidence, all addressable without rearchitecting.

## What to fix first

1. Core text detection uses case-folded substring matching in BOTH the hierarchy and OCR channels, so a real failure (e.g. login did not succeed) can be graded PASS and working software graded FAIL — the worst class of defect for a trust-focused QA tool, and it is invisible to the test author (validator.py:187, ocr.py:147).
2. The local web control panel has no auth/CSRF/Origin check and is drivable from any page the engineer visits: it interpolates an untrusted package name straight into a device shell (command execution on the emulator) and joins request-supplied paths without confinement (arbitrary host-file read and arbitrary-APK install) (server.py:355, 265, 178).
3. long_click is advertised and reported as PASS but actually performs a short tap — a silent gesture mismatch that mis-verdicts every long-press flow (multi-select, context menu, drag) (executor.py:217).
4. Evidence and library durability lose data silently: a same-second run_id overwrites a prior run's entire report/step artifacts, and screen-library/selector-cache saves are non-atomic, race-prone under the threaded server, and swallow OSError — the exact artifacts the tool exists to accumulate can disappear while reporting success (evidence.py:32, screen_library.py:176).
5. Robustness gaps destroy or invert the deliverable: an unexpected exception in an assert step propagates out of run() and crashes with zero report/evidence, and a loader-blessed element_exists+value assertion always FAILs regardless of screen content (runner.py:80, loader.py:85).
6. The test suite gives false confidence on the trust-critical paths: the keyboard-dismiss recovery test asserts nothing and never runs the branch it names, element click/set_text cache-invalidation is untested, and the perf guards do not exercise the uncached app_current/dumpsys/logcat round-trips they claim to bound (test_resolver_recovery.py:56, test_device_cache.py:64, perf.py:115).

## Remediation roadmap

### Now

- Replace substring text matching with explicit equals/contains semantics in validator._hierarchy_has_text and ocr.ocr_find (make single- and multi-token matching consistent, strip punctuation in normalisation), so both perception channels agree and false PASS/FAIL on text is eliminated.
- Make activity_is strict: drop the `expected in activity` branch, keep exact equality plus a component-boundary endswith so an adjacent/error activity no longer grades PASS.
- Add a per-session token plus Origin/Host validation to every mutating webapp endpoint, validate `package` against ^[A-Za-z0-9_.]+$ (and prefer u2 app_start over interpolated `adb shell monkey`), and confine test/apk request paths under ROOT via os.path.realpath rejecting absolute/`..` inputs.
- Fix long_click to call a real long-press primitive on the Device/Element seam (u2 long_click), or reject long_click in the loader rather than silently degrading to a tap and reporting PASS.
- Guard element_exists+value in loader._validate_step (require at least one of id/text/desc) so a loader-blessed assertion can no longer always FAIL.
- Wrap each runner step's execute/_run_assert in try/except (mirroring executor.execute) so an unexpected exception becomes a FAIL/DEVICE_ERROR with evidence, timeline and report still written, and coerce assertion value to str.

### Next

- Make run_id collision-proof (uuid/microsecond suffix) or have Evidence refuse an already-populated run_dir, so concurrent same-second runs cannot overwrite each other's report and artifacts.
- Make ScreenLibrary.save and SelectorCache.save atomic (temp file + os.replace) with a single-writer/lock, stop swallowing OSError, and distinguish corrupt-vs-absent on load instead of silently resetting to empty.
- Harden settle(): require the screen to first differ from the pre-action baseline (or enforce a minimum duration / N>=2 stable pairs) and treat a None/failed dump as not-stable, so a stale or double-failed read cannot be graded 'stable'.
- Add real tests for the keyboard-dismiss recovery branch, element click/set_text cache invalidation via a real _U2Element, and not_visible OCR (including the OCR-unavailable case surfacing an indeterminate/DEVICE_ERROR rather than a silent PASS).
- Fix crawler._return to accept the returned screen when it matches EITHER the top fingerprint or the pre-tap fingerprint (or re-scroll to top before comparing) and continue rather than break, so below-the-fold candidates are not abandoned.

### Later

- Cut redundant OCR: gate _collect_ocr on validated_by=='ocr', reuse the ocr_find result already computed in validator._ocr, and add an lru_cache on _load_words keyed by (path, mtime).
- Read logcat incrementally (offset/-t tail) instead of re-dumping and re-scanning the full buffer after every step.
- Memoize current_package and keyboard_visible under the hierarchy memo, pass before.keyboard_visible into _hide_keyboard, and reduce the crawler's per-candidate re-scroll passes to about one per direction.
- Replace the SequenceMatcher hierarchy diff with fingerprint-based change detection, strip hierarchy_xml/screenshots from the inlined raw timeline, and use counts.get('status', ...) in report.render so one malformed step cannot abort the whole report.
- Strengthen the perf guards to bound the real app_current/dumpsys/logcat round-trips through AndroidDevice.observe and add a nested-hierarchy fixture so rank_candidates' ancestor walk is actually measured.

## What holds up

- Dual-channel perception (accessibility tree first, screenshot+OCR fallback) backed by a structured recovery ladder is a genuinely strong, deterministic architecture for UI validation — the right design for the trust the tool is chasing.
- Defensive engineering is already present in key places: executor.execute wraps its dispatch, a HIERARCHY_CACHE memo exists for back-to-back reads, and evidence capture plus self-contained HTML reports are real, working deliverables.
- A FakeDevice-based pytest suite and dedicated complexity/perf guards exist — the scaffolding for trustworthy, cost-aware testing is in place even where individual tests are currently weak.
- Adversarial verification refuted many candidate findings, so large parts of the resolver, executor and validation logic held up under scrutiny — the failures are specific and fixable, not systemic rot.
- The web panel binds only to 127.0.0.1 and uses list-based host argv, so the host shell is not directly injectable; the security exposure is real but bounded (device-shell / cross-site) rather than full host RCE.
- The codebase is clearly written with the QA-trust and device-round-trip-cost model in mind, which makes the identified defects sharply scoped and the remediation path clear.

## Findings

### Detection accuracy

#### 🔴 HIGH · text_exists / not_visible use naive substring containment -> false PASS

`engine/validator.py:187` · _correctness_ · verdict: **CONFIRMED**

**What's wrong.** Hierarchy text matching for the text_exists and not_visible assertions is a case-folded substring test (`want in text.lower()`), not a word/exact match. Any expected string that happens to be a substring of a longer on-screen word or phrase is treated as present. This directly produces false PASS on text_exists and false FAIL on not_visible, and the same loose matching feeds the OCR fallback for text_exists (validator._ocr -> ocr.ocr_text_exists).

**How it goes wrong.** A login test asserts text_exists value 'Logged in'. The app's failed-login screen shows the literal text 'Not logged in yet'. `'logged in' in 'not logged in yet'` is True, so the assertion returns PASS — a real login failure is reported as success. Symmetrically, not_visible value 'Cart' fails (reports 'still visible') on a screen showing 'Shopping Cart is empty', a false FAIL of working software.

**Why it matters.** This is the worst class of defect for a trust-focused QA tool: a genuine functional failure (login did not succeed) is graded PASS, and correct behaviour can be graded FAIL. The substring semantics are invisible to the test author, who reasonably expects text_exists to mean 'this text is present'.

**Evidence.** engine/validator.py:185-189 `_hierarchy_has_text`: `want = expected.strip().lower()` then `for text in Observation(...).texts(): if want in text.lower(): return True`. Called by text_exists (line 93: `if _hierarchy_has_text(after.hierarchy_xml, expected)`) and by not_visible (line 152: `if _hierarchy_has_text(after.hierarchy_xml, expected): return FAIL ...still in hierarchy`).

**Reproduction.** text_exists value 'Success' against a hierarchy node text='Unsuccessful' -> `'success' in 'unsuccessful'` is True -> Status.PASS (false PASS). Symmetric false FAIL: not_visible value 'Cart' against node text='Shopping Cart is empty' -> `'cart' in 'shopping cart is empty'` True -> FAIL 'still in hierarchy'. Same as finding's 'Logged in' in 'Not logged in yet'.

**Fix.** Match against whole normalised text values or word-boundary tokens rather than raw `in`. E.g. compare `want == text.lower().strip()` for exact assertions, or split into words and require a contiguous token-sequence match; expose an explicit `contains` vs `equals` mode instead of silently doing substring. Apply the same fix to the OCR path so both perception channels agree.

#### 🔴 HIGH · OCR single-token match is substring-based and inconsistent with multi-word matching

`engine/ocr.py:147` · _correctness_ · verdict: **CONFIRMED**

**What's wrong.** In ocr_find, a single-token target matches when the target is a substring of any OCR word (`target[0] in w["norm"]`), whereas a multi-word target requires exact token equality (`[x["norm"] for x in window] == target`). A single query word therefore matches inside unrelated longer words, while a two-word query is intolerant of any punctuation/OCR noise. Detection accuracy silently depends on how many words the assertion value contains.

**How it goes wrong.** ocr_text_exists value 'OK' returns found=True on a screen whose only text is 'Facebook' ('ok' is a substring of 'book') at normal Tesseract confidence >= 0.60, a false PASS. In the resolver, target label 'Pay' OCR-matches and taps the word 'Repay' or 'Display'. Conversely, ocr_text_exists value 'Payment successful' returns not-found when OCR reads 'Payment Successful!' (norm 'successful!' != 'successful'), a false FAIL, even though the single word 'successful' would have matched via substring.

**Why it matters.** Both false PASS (single-word substring) and false FAIL (multi-word exactness) originate here, plus mis-directed taps in the resolver OCR fallback, which then corrupt every downstream verdict for that step. The behaviour is non-obvious and word-count-dependent, undermining trust in the OCR channel that exists specifically to catch text the tree hid.

**Evidence.** engine/ocr.py:144-149 single-token branch: `if w["norm"] == target[0] or target[0] in w["norm"]: ... matches.append(...)`. engine/ocr.py:151-153 multi-word branch: `window = line_words[start:start + span]` then `if [x["norm"] for x in window] == target:`. This function backs both validator.ocr_text_exists (verdicts) and resolver.best_match (tap coordinates).

**Reproduction.** Call ocr_text_exists(img, "OK") on a screen whose only text is "Facebook": target=["ok"], span==1, norm "facebook" contains substring "ok" (chars o,o,k) so target[0] in w["norm"] is True -> match at the word's confidence; at Tesseract conf>=0.60 ocr_text_exists returns (True, conf) => false PASS. Conversely ocr_text_exists(img, "Payment successful") when OCR reads "Payment" + "Successful!" gives window norms ["payment","successful!"] != ["payment","successful"] => no match => false FAIL, though single word "successful" would have matched by substring. In resolver.best_match, query "Pay" matches OCR word "Repay" ("pay" in "repay") and taps its center.

**Fix.** Make single-token and multi-token matching consistent: for a single word require whole-word equality (`w["norm"] == target[0]`) by default, and strip punctuation in `_normalise` (e.g. `re.sub(r"[^\w\s]", "", s)`) so multi-word windows tolerate trailing '!'/':'. If substring/contains behaviour is desired, make it an explicit opt-in flag rather than the implicit single-token default.

#### 🟠 MEDIUM · settle() declares a stale, pre-update screen 'stable' (premature settle)

`engine/stabilize.py:41` · _robustness_ · verdict: **CONFIRMED**

**What's wrong.** settle() returns True as soon as two consecutive hierarchy dumps (~0.3s apart) are equal and the activity is unchanged. It never compares against the pre-action baseline and requires no minimum settle time, so a screen that has not yet begun an asynchronous update reads as 'settled'. Additionally, because each read is wrapped in `_safe` (returns None on error), two consecutive failed dumps compare equal (None == None) and are also reported as 'stable'.

**How it goes wrong.** A tap triggers a network call; the screen stays visually and structurally identical for ~0.5s, then renders results. settle's first pair of dumps at t=0.3 and t=0.6 are both the old screen, compare equal, and settle returns at t=0.6 — before the update lands. observe() then captures the old screen as 'after', and text_exists for the new content returns FAIL (false FAIL). Separately, if uiautomator2 raises on two dumps during a transition, both are None, stable=True, and a mid-transition screen is captured.

**Why it matters.** The 'after' observation that every assertion is graded against can be a stale or transitional screen, yielding false FAIL (expected content not yet present) or false PASS (e.g. not_visible passing because the element that is about to appear has not rendered). This intermittently corrupts verdicts on any app with async loading.

**Evidence.** engine/stabilize.py:36-47: after `prev_xml = _safe(d.dump_hierarchy)`, the loop does `sleep(interval)`, re-reads, then `stable = cur_xml == prev_xml and cur_act == prev_act; ... if stable: return True`. There is no comparison to the screen state before the action and no lower bound on elapsed time. executor.py:188 calls `settled = settle_fn(d)` immediately after `_perform` with no post-action delay.

**Reproduction.** Test: [tap target 'Load'] then [assert text_exists 'Results']; the tap fires a fetch with no spinner/structural change and results render at t~0.5s. With interval=0.3, settle compares dump@0.0 vs dump@0.3 (both old screen), returns True at t=0.3; executor and the immediately-following assert both observe the old screen (~t=0.3), and text_exists 'Results' FAILs on working software (false FAIL). Inverse: assert not_visible passes before the element renders (false PASS).

**Fix.** Require the screen to first differ from the pre-action baseline (or enforce a minimum settle duration / N>=2 consecutive stable pairs) before declaring stability, and treat a None/failed dump as 'not stable' rather than equal, so two read errors cannot masquerade as a settled screen.

#### 🟠 MEDIUM · activity_is matches on substring, passing on the wrong activity

`engine/validator.py:215` · _correctness_ · verdict: **CONFIRMED**

**What's wrong.** _activity_matches accepts an activity when the expected value is merely a substring of the current activity (`expected in activity`), in addition to exact and endswith matching. A short or partial expected value therefore passes on a different, longer activity that contains it.

**How it goes wrong.** activity_is value 'CartActivity'. The user tapped through to '.CartEmptyActivity' (an error/empty path) instead of the expected '.CartActivity'. `'CartActivity' in 'com.app.CartEmptyActivity'`? no — but `activity_is value 'Cart'` (a common shorthand) passes on '.CartEmptyActivity', '.ShoppingCartActivity' and '.CartErrorActivity' alike, so the test cannot distinguish the intended destination from a wrong one.

**Why it matters.** activity_is is meant to be the exact, deterministic screen-identity check. The substring branch makes it non-strict, so landing on an adjacent/error activity whose name contains the expected token is graded PASS — a false PASS on navigation correctness.

**Evidence.** engine/validator.py:212-215 `_activity_matches`: `return activity == expected or activity.endswith(expected) or expected in activity`. Used by the activity_is assertion at line 130.

**Reproduction.** validator.validate({"type":"activity_is","value":"Cart"}, before, after) with after.activity="com.example.shop/.ShoppingCartActivity" returns Status.PASS (exact and endswith fail; "Cart" in the string is True) despite the intended destination being .CartActivity.

**Fix.** Drop the `expected in activity` branch. Keep exact equality plus endswith on a component boundary (e.g. require the char before the match to be '.' or '/'), so 'MainActivity' matches 'com.app.MainActivity' but 'Cart' does not match 'ShoppingCartActivity'.

#### 🔵 LOW · rank_candidates truncates to 5 by score before resolver's role/base filter, dropping the correct target

`engine/inspect.py:315` · _correctness_ · verdict: **UNVERIFIED**

**What's wrong.** rank_candidates sorts by score (base text similarity plus role/enabled bonuses) and truncates to `limit` (default 5) before returning. The resolver only afterwards filters those survivors by `base >= RESOLVE_MIN_SCORE and _role_ok(role)`. Because the truncation happens first and role is only a small additive bonus (not a filter) inside ranking, a correct-role target with a slightly lower base can be pushed past position 5 by wrong-role elements and silently discarded, so the resolver never sees it.

**How it goes wrong.** role='tappable', query 'Submit'. The screen has five non-clickable TextViews whose text exactly contains 'Submit' (base 1.0, score ~1.0) plus one clickable Button whose visible text is a fuzzy variant like 'Submit form' (base ~0.7, score ~0.8). The five labels fill the top-5 by score; the Button is truncated out. resolver's role filter then finds zero acceptable clickable candidates and returns NOT_FOUND -> the step is graded BLOCKED though a valid target exists.

**Why it matters.** A resolvable, correct-role control can be reported unreachable, producing a false BLOCKED (which aborts the run and marks later steps SKIPPED) or an OCR/coordinate fallback tap on the wrong spot. Narrow in practice, but it degrades the resolver's central job of finding the right element.

**Evidence.** engine/inspect.py:306-317: `cands.sort(key=lambda c: c.score, reverse=True)` then break once `len(unique) == limit` (limit default 5 at line 261). engine/resolver.py:144,157-158: `cands = inspect_mod.rank_candidates(query, elements, role=role)` (no larger limit passed), then `acceptable = [c for c in cands if c.base >= RESOLVE_MIN_SCORE and _role_ok(c.element, role)]`.

**Fix.** Apply role and base acceptance before truncating (filter role-fit and base>=MIN, then take the top N), or have the resolver request a larger/unbounded candidate list and do the trimming after its own role/base filter. Passing role as a hard pre-filter for the target action would also prevent wrong-role elements from consuming candidate slots.

### Crawl / exec / recovery

#### 🟠 MEDIUM · Unguarded assert step aborts the whole run and discards the report

`engine/runner.py:80` · _robustness_ · verdict: **CONFIRMED**

**What's wrong.** The per-step loop and _run_assert have no try/except, unlike executor.execute which defensively wraps its dispatch (executor.py:129-186). Any exception raised inside validator_mod.validate (runner.py:134) therefore propagates out of run(), so no report.html, timeline.json, logcat.txt or selector cache is ever written. The runner's own docstring promises it persists evidence and the HTML report and marks remaining steps SKIPPED; an unexpected raise breaks that contract and the tool exits with a traceback instead of a verdict.

**How it goes wrong.** A loader-valid test case with `- assert: {type: text_exists, value: 100}` (e.g. asserting an order total or item count appears). Loader accepts it; runner calls validate -> _hierarchy_has_text(xml, 100) -> `(100).strip()` raises AttributeError; the exception is caught nowhere, run() aborts mid-loop, and NO report/timeline/logcat/bindings are produced for the run. activity_is with a numeric value fails the same way via `activity.endswith(expected)` (validator.py:215).

**Why it matters.** For a QA tool whose entire deliverable is the self-contained report, a single valid-but-numeric assertion turns a run into a hard crash with zero evidence persisted, instead of a clean FAIL. Users lose all results for the run and see a stack trace rather than a verdict.

**Evidence.** runner.py:79-81 `if "assert" in step:` -> `res = _run_assert(device, step["assert"], last_before, last_after, after_path, _safe_logcat(device))` with no surrounding try/except in the loop (68-98) or in _run_assert (123-166). _run_assert calls `outcome = validator_mod.validate(...)` (runner.py:134). validator.text_exists does `want = expected.strip().lower()` (validator.py:186) after only guarding `if not xml or not expected`. loader.py:85-87 accepts any non-empty/non-None `value`, so a numeric value passes validation.

**Reproduction.** Loader-valid test case with `- assert: {type: text_exists, value: 100}` run on a device whose hierarchy dump is non-empty: validate -> _hierarchy_has_text(xml, 100) -> (100).strip() raises AttributeError, propagates out of run(), and no report.html/timeline.json/logcat/bindings are written (verified with FakeDevice).

**Fix.** Wrap each step's execute/_run_assert in try/except inside the runner loop (mirroring executor.execute), converting an unexpected exception into a FAIL/DEVICE_ERROR ActionResult so evidence, timeline and report are still written; additionally coerce assertion `value` to str in the loader or validator.

#### 🟠 MEDIUM · long_click silently performs a short tap while reporting PASS

`engine/executor.py:217` · _correctness_ · verdict: **CONFIRMED**

**What's wrong.** long_click is a first-class, documented action (docs/index.html:379 'long-press'; TEST_GUIDE.md:377; loader TARGETED_ACTIONS) that the executor dispatches, but _perform executes a plain click() (a short tap), not a long-press. There is no long-press primitive on the Device/Element interface at all. The step still resolves the target, performs the tap, and returns Status.PASS with resolved_by set, so the report claims a long-press was carried out when it was not.

**How it goes wrong.** A test does `- action: long_click, target: "Photo"` to open a context menu, then `- assert: {type: element_exists, id: .../context_menu}`. The executor short-taps the photo (opening a detail view, or doing nothing), marks the long_click step PASS, and the context-menu assert FAILs — a false FAIL blamed on the app though the tool never long-pressed. If the short tap happens to reveal a same-id element, it is a false PASS.

**Why it matters.** A trust-breaking gesture mismatch: the tool advertises and reports long-press support but executes a different gesture and calls it PASS, producing false FAILs (or false PASSes) on any long-press-dependent flow (multi-select, context menu, drag handle).

**Evidence.** executor.py:215-217 `elif action == "long_click": if res.element is not None: res.element.click()  # element long-click optional; click is the MVP` and the OCR branch `else: d.tap_xy(*res.coordinates)` — both are ordinary taps. Device.Element (device.py:46-59) exposes only click/set_text/center/exists; no long-click exists.

**Reproduction.** A valid, loader-accepted test case `steps: [{action: long_click, target: "Photo"}, {assert: {type: element_exists, id: .../context_menu}}]` short-taps "Photo" (element.click()/tap_xy) instead of long-pressing, marks the long_click step PASS with resolved_by set (report claims a long-press was performed), and the context-menu assert then FAILs — a false FAIL blamed on the app that never got a long-press; if the short tap happens to expose a same-id element it is instead a false PASS.

**Fix.** Add a real long_click to the Device/Element seam (u2 supports element.long_click() and d.long_click(x, y, duration)) and call it from _perform; until then, reject long_click in the loader/executor rather than silently degrading to a tap.

#### 🟠 MEDIUM · Crawler abandons a screen after exploring any below-the-fold candidate

`engine/crawler.py:268` · _correctness_ · verdict: **CONFIRMED**

**What's wrong.** After tapping a candidate that was scrolled into view and exploring the resulting screen, the crawler calls _return(fp) where fp is the screen's TOP entry fingerprint (crawler.py:216). But the candidate was reached by scrolling, and pressing Back typically restores the parent screen at its previous (scrolled) scroll position, whose structural_fingerprint differs from the top's (the visible node set changed). _return then returns False and the candidate loop `break`s, so every remaining candidate on that screen is never tried.

**How it goes wrong.** Crawl a product-list app where 'ADD TO CART' is below the fold. _gather discovers it; the loop scrolls down (pre_fp = scrolled), taps it, captures the cart/detail screen, then _return(fp) presses Back. The list is restored scrolled-down (fingerprint != top fp) so _return returns False and the loop breaks — the remaining products, the checkout entry, and nav chrome on that screen are never explored, silently under-capturing exactly the scroll-heavy screens the scroll-aware feature targets.

**Why it matters.** Systematic under-coverage of the crawler on any screen where an explored action sits below the fold and Back preserves scroll position (the common RecyclerView/list case) — the discovery tool quietly stops after one sub-fold tap per screen, defeating the context-aware/scroll-aware ordering it was built for.

**Evidence.** crawler.py:238 `el = _bring_into_view(sig)` scrolls down to reveal the candidate; crawler.py:244 `pre_fp = here.structural_fingerprint()` is the scrolled fingerprint; crawler.py:268 `if not _return(fp): break` compares to `fp` (the top fingerprint from line 216). _return (133-139) does one Back + `obs.structural_fingerprint() == expected_fp`. structural_fingerprint (inspect.py:150-154) hashes the sorted resource_id:cls:content_desc of ALL parsed elements, so it changes when scrolling reveals/hides list rows.

**Reproduction.** Crawl a scrollable product screen with candidates [A above-fold→X, B below-fold→Y, C below-fold]; A is tapped and returns to top fine, then B is scrolled into view (pre_fp=scrolled), tapped→Y, explored, then _return(fp) presses Back; a real RecyclerView/NestedScrollView restores the screen still scrolled so its fingerprint != top fp, _return returns False, the loop breaks, and C (plus any later nav chrome) is never tapped.

**Fix.** Have _return accept success when the returned screen matches EITHER the top fp or the pre-tap pre_fp (or re-scroll to top and re-observe before comparing), and `continue` to the next candidate instead of breaking when only the scroll position differs.

#### 🔵 LOW · Keyboard-dismiss via press_back can navigate off the screen under test

`engine/executor.py:48` · _correctness_ · verdict: **PLAUSIBLE**

**What's wrong.** Both the executor's pre-tap _hide_keyboard and recovery stage 3 dismiss an open soft keyboard by pressing hardware Back. On most screens Back only closes the IME, but when the keyboard is already animating closed, or the IME is in fullscreen/extract mode, or a dialog has focus, Back instead pops the Activity/dialog, moving off the screen under test. The following resolve/tap then runs against the wrong screen.

**How it goes wrong.** A login test types into the password field (keyboard open) then `- action: tap, target: "Login"`. _hide_keyboard sees the keyboard visible and presses Back; on a device/IME where that Back dismisses the login dialog or pops the Activity, the subsequent resolve for 'Login' either fails (false FAIL blamed on the app) or matches a 'Login' control on the now-foreground previous screen and taps it (false PASS / wrong action).

**Why it matters.** A false FAIL or a wrong-screen tap that can cascade into a misleading PASS/FAIL — a trust defect that is hard to spot because the report shows a normal tap step.

**Evidence.** executor.py:44-52 `_hide_keyboard`: `if d.keyboard_visible(): d.press_back(); sleep(0.3)` — invoked for tap/submit/long_click (executor.py:136-137). recovery.py:82-85 repeats it: `if _safe(d.keyboard_visible): ... d.press_back()`. No re-check that the screen/activity survived the Back; device.py exposes no dedicated hide-keyboard call.

The server is a ThreadingHTTPServer, so concurrent /api/inspect and /api/crawl requests for the same package each construct their own ScreenLibrary, load, mutate, and save() — a last-writer-wins read-modify-write race that drops captures. A crash/Ctrl-C mid-write, or a reader (/api/screens) hitting a half-written file, leaves corrupt JSON; __init__ then silently resets the whole library to empty via `except (OSError, ValueError): pass`. SelectorCache.save (selector_cache.py:44) has the identical pattern.

**How it goes wrong.** Two capture POSTs for com.foo overlap: A loads {s1}, B loads {s1}, A adds s2 and saves {s1,s2}, B (still holding {s1}) adds s3 and saves {s1,s3} — s2 is lost. Or: disk full / read-only dir → save() raises OSError → swallowed → _capture returns `{"id":..., "screens": N}` reporting success while nothing reached disk; next session the capture is gone.

**Why it matters.** Silent data loss and false success reporting for the exact asset the tool exists to accumulate (captured screens/selectors). A capture that 'succeeded' vanishing, or the whole library silently resetting to empty after a corrupt write, directly breaks the tool's trust guarantee.

**Evidence.** Lines 176-182: `def save(self):\n    try:\n        os.makedirs(self.dir, exist_ok=True)\n        with open(self.path, "w", encoding="utf-8") as fh:\n            json.dump(self.data, fh, ...)\n    except OSError:\n        pass`. Load path (lines 44-50): `with open(self.path) ... loaded = json.load(fh) ... except (OSError, ValueError): pass` — a corrupt/partial file is indistinguishable from 'no library' and self.data stays the empty default `{"package": package, "screens": []}`.

**Reproduction.** Make screens/<pkg> read-only (or fill the disk), then POST /api/inspect: _capture's lib.save() raises OSError, swallowed at screen_library.py:181, and the endpoint returns {"id":…, "screens":1} success while nothing is written; independently, two overlapping POST /api/inspect (or /api/inspect + /api/crawl) for the same package each load-mutate-save separate ScreenLibrary instances and the second save drops the first capture; and Ctrl-C during json.dump leaves a partial file that the next __init__ silently reads as an empty library.

**Fix.** Write to a temp file in the same dir and os.replace() it over the target (atomic on POSIX/Windows); serialize writes with a per-path lock or a single-writer; on load, distinguish 'file present but unparseable' from 'absent' and surface an error instead of silently resetting; do not swallow OSError in save() — propagate so callers do not report false success.

#### 🟠 MEDIUM · Device-side command injection via package in /api/launch

`webapp/server.py:265` · _security_ · verdict: **CONFIRMED**

**What's wrong.** _launch interpolates the untrusted `package` request field into an `adb shell monkey -p <package> ...` argv. adb concatenates everything after `shell` and hands it to the device's /system/bin/sh, so shell metacharacters in `package` execute as separate device-shell commands. The host argv is a list (host shell safe), but the device shell is not protected.

**How it goes wrong.** POST /api/launch with `{"package":"com.x; input keyevent 26; am force-stop com.bank"}`. The emulator shell runs `monkey -p com.x`, then `input keyevent 26`, then `am force-stop com.bank`. Reachable remotely via the CSRF gap in finding 1.

**Why it matters.** Arbitrary command execution on the connected emulator/device (screen off, force-stop apps, clear data, etc.), triggerable cross-site given the missing origin check — corrupts device state a run depends on and can silently invalidate results.

**Evidence.** Lines 263-266: `adb = shutil.which("adb") or "adb"\n cmd = [adb] + (['-s', serial] if serial else []) + ['shell', 'monkey', '-p', package, '-c', 'android.intent.category.LAUNCHER', '1']\n out = subprocess.run(cmd, ...)`. `package` comes straight from `payload["package"]` (do_POST line 373). The device shell receives `monkey -p <package> -c android.intent.category.LAUNCHER 1` as one string.

**Reproduction.** POST http://127.0.0.1:8765/api/launch with body {"package":"x;am force-stop com.android.chrome #"} (sent as text/plain to make it a CSRF-simple request; server parses body as JSON regardless). adb sends `monkey -p x;am force-stop com.android.chrome # -c android.intent.category.LAUNCHER 1` to the device shell, which runs `monkey -p x` then the injected `am force-stop com.android.chrome`, the `#` commenting out the trailing args.

**Fix.** Validate `package` against a strict package-name regex (`^[A-Za-z0-9_.]+$`) before use, and prefer uiautomator2's app_start (as AndroidDevice.launch already does) over `adb shell monkey` with an interpolated string.
