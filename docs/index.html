1 · What it is

A runner that takes one APK + one YAML test case and, on a connected device/emulator, installs the app, walks the steps (tap / type / swipe), and after every step perceives the screen two ways — the accessibility tree (UI hierarchy) and a screenshot read by OCR — then validates each expected outcome with a fixed, deterministic algorithm. It writes per-step evidence (before/after screenshots, hierarchy XML, OCR matches) and a single report.html.

APK + testcases/login.yaml │ ▼ cli.py ──▶ check env ──▶ connect device ──▶ install APK │ ▼ for each step: ├─ observe(before) one ScreenObservation: elements · fingerprint · window ├─ act resolve: id(EXACT) → cache → label-rank → OCR, then tap/type/submit ├─ settle wait until the screen is stable ├─ observe(after) └─ validate hierarchy → OCR → change (per assertion, fixed order) │ ▼ reports/<run_id>/report.html every step: resolved_by, validated_by, evidence
The engine touches Android only through engine/device.py. That single seam is why the whole engine is unit-tested against a fake device with no hardware, and why the same code runs unchanged on a real device.

★ Old engine → new engine

The runner started as a fixed pipeline: a step named an exact resource-id, the resolver looked it up, tapped it, done. It worked, but every test was welded to one app version — rename an id and the test broke, and writing a test meant hand-dumping the hierarchy to copy ids first.

The rework turns that pipeline into a shared Perception → Resolution → Action → Observation → Validation loop. One ScreenObservation is built per screen and reused by execution, recovery, validation and the new inspect mode. You now write intent (the visible label); the engine perceives the live screen, ranks it, binds the real id, and remembers it.

Nothing about the device seam changed. The engine still talks to Android only through engine/device.py, so the whole new loop is still unit-tested against a fake device — py -m pytest -q.

Live findings (device/app limits, not engine bugs), kept for the record:
  • Aimring launches then shows “Google Play not enabled” — it's wrapped by com.pairip.licensecheck (Play's app-integrity DRM), which blocks sideloaded installs. Runs only when installed from Play (or from an unprotected dev build).

3 · Quick start

a. Get an APK

Either build the bundled sample app, or drop in any APK you trust:

.\sample-app\build.ps1                 # → sample-app\build\shop-login.apk
aapt dump badging <app>.apk | Select-String "package:|launchable-activity:"

The package and launchable-activity it prints go into your YAML.

b. Boot the emulator

emulator -avd qa_test -no-audio -no-snapshot -gpu swiftshader_indirect
adb wait-for-device
do { Start-Sleep 3; $b = adb -s emulator-5554 shell getprop sys.boot_completed } until ($b -match '1')

c. Run

py cli.py --dry-run --test testcases\login.yaml          # preview plan, no device
py cli.py --apk sample-app\build\shop-login.apk --test testcases\login.yaml

Expect Overall: PASS and a report path. Open the report.html.

4 · How the flow works

Each step is either an action (change the app) or an assert (check the result). For an action the runner:

  1. observe(before) — snapshot the screen.
  2. resolve the target with recovery: id/text/desc (EXACT) → cache (learned binding) → label ranking → OCR; if none hit, wait/retry, dismiss the keyboard, scroll, dismiss a blocking dialog, and re-resolve. If still nothing → BLOCKED with a failure_reason + ranked suggestions.
  3. perform the action (tap the element or the OCR coordinates; type; swipe).
  4. settle — wait until two hierarchy dumps match (optionally until frames are pixel-idle).
  5. observe(after), then a crash gate: a FATAL line in logcat → CRASH.

An assert runs the fixed-order validator (crash gate always first):

AssertHow it is decidedvalidated_by
text_existshierarchy contains it → else OCR ≥ threshold → else FAILhierarchy / ocr
ocr_text_existsOCR onlyocr
element_existsa node matches the id/text/deschierarchy
activity_iscurrent activity matcheshierarchy
screen_changedbefore→after change ratio ≥ CHANGE_MINchange
Why this matters: change detection is the only thing screen_changed uses, and it is never a fallback for the others. Tapping “Login” and landing on an error screen changes the screen but must not pass a text_exists("Welcome"). That guard is tested.

5 · The test-case language (YAML)

A test case is one YAML file. Skeleton:

name: "Human-readable test name"        # required
package: com.example.shop               # required — the app under test
launch_activity: null                   # null = use the APK's launchable activity

data:                                   # optional — {{key}} is substituted into 'value'
  email: test@example.com
  password: Password123

steps:                                  # required — a non-empty list
  - action: launch
  - action: type
    target: { id: "com.example.shop:id/email" }
    value: "{{email}}"
  - assert:
      type: text_exists
      value: "Welcome"

Actions

actionneedsdoes
launch—start the app (fresh, plants a logcat baseline)
taptargetclick the resolved element / OCR coordinate
typetarget, valueset text into the field
enter_texttarget, valuetype by label (field found by ranking); role = field
submit— (or target)find + tap a submit control (Login/Continue/Next…); hides keyboard first
long_clicktargetlong-press
swipefrom,to (or none)swipe between coords; with no coords it scrolls forward
back—press system Back
waitsecondspause (e.g. for an animation/network)

Targets (selectors) — how an element is found

A target is either a string label (the new, preferred way) or a mapping of explicit keys. A string is treated as { label: … }: the engine ranks it against the live screen, binds the real element, and caches it.

keymatchesexample
(string)label — ranked against text/desc/id of every live elementtarget: "Email"
labelsame as a bare string, in mapping form{ label: "Email" }
idresource-id (exact) → EXACT{ id: "com.app:id/email" }
textvisible text — exact, then “contains”{ text: "Login" }
desccontent-description (accessibility label){ desc: "Submit" }
ocrforce an OCR search for this text (else falls back to text){ ocr: "PAY NOW" }

Resolution order is id/text/desc (EXACT) → cache (learned) → label ranking → OCR. Explicit keys still win when you want a hard pin; a label is what makes a test survive id churn. The learned label → id map is written to reports/<run>/bindings.json.

Asserts

- assert: { type: text_exists,      value: "Welcome" }      # hierarchy → OCR
- assert: { type: not_visible,      value: "Loading" }      # NEW — text is gone
- assert: { type: ocr_text_exists,  value: "PAY NOW" }      # OCR only (painted text)
- assert: { type: element_exists,   id: "com.app:id/otp" }  # or text:/desc:
- assert: { type: activity_is,      value: ".NafathActivity" }
- assert: { type: activity_changed }                         # NEW — activity differs before→after
- assert: { type: screen_changed }                           # a state transition happened

Data interpolation

{{key}} in a step's value is replaced from data. Use it to keep credentials/inputs in one place (and to reuse a test with different data).

6 · Writing a test from a QA test-case doc

Your QA docs already have the structure the runner needs. A test-case table is:

Test Steps → actions  ·  Expected Results → asserts  ·  Test Data → data: + {{…}}  ·  Precondition → the steps you run first (or a prior test case).

The recipe:

  1. Read the Test Steps column top-down. Each row that does something is an action; each row that checks something is an assert.
  2. For each action, find the on-screen target's id/text (see §10).
  3. Turn every Expected Result into an assert — usually text_exists for a shown string, activity_is for a screen change, element_exists for a control being present.
  4. Put inputs (email, OTP, NID…) in data.

7 · Worked example — a sign-up flow

Say the QA doc says: open the app → tap “Sign up” → enter name, email, password → tap “Create account” → a verification screen shows “Verify your email”. That becomes:

name: "Sign up with valid details"
package: com.example.shop
launch_activity: null

data:
  name: "Test User"
  email: "new.user@example.com"
  password: "Password123"

steps:
  - action: launch

  - action: tap
    target: { text: "Sign up" }          # or { id: "com.example.shop:id/signup" }

  - action: type
    target: { id: "com.example.shop:id/name" }
    value: "{{name}}"

  - action: type
    target: { id: "com.example.shop:id/email" }
    value: "{{email}}"

  - action: type
    target: { id: "com.example.shop:id/password" }
    value: "{{password}}"

  - action: tap
    target: { text: "Create account" }

  # Expected result → asserts
  - assert: { type: activity_is,  value: ".VerifyEmailActivity" }
  - assert: { type: text_exists,  value: "Verify your email" }

Negative sign-up (duplicate email → inline error) is the same file with a different expected result — and the validator will correctly FAIL if you assert the success text on the error screen:

  - action: tap
    target: { text: "Create account" }
  - assert: { type: text_exists, value: "Email already registered" }   # the real outcome
  - assert: { type: screen_changed }                                    # something happened

8 · Worked example — your Nafath story

Mapping Test Case 1 (“login → redirect to Nafath screen”, validate the screen content) from the sample story. The precondition (login + OTP) runs as the first steps; then each “Validate …” row becomes a text_exists assert. Because the copy exists in English and Arabic, you assert both — the runner matches Unicode text in the hierarchy directly.

name: "GAM: Login passes OTP and lands on Nafath verification"
package: net.geidea.app
launch_activity: null

data:
  email: "qa.user@geidea.net"
  password: "ValidPass123"
  otp: "123456"

steps:
  - action: launch

  # --- precondition: login (GAM-201) ---
  - action: type
    target: { id: "net.geidea.app:id/email" }
    value: "{{email}}"
  - action: type
    target: { id: "net.geidea.app:id/password" }
    value: "{{password}}"
  - action: tap
    target: { text: "Login" }

  # --- precondition: OTP ---
  - action: type
    target: { id: "net.geidea.app:id/otp" }
    value: "{{otp}}"
  - action: tap
    target: { text: "Verify" }

  # --- Expected: redirected to Nafath verification ---
  - assert: { type: activity_is, value: "NafathVerification" }

  # Title (EN + AR)
  - assert: { type: text_exists, value: "Nafath Verification" }
  - assert: { type: text_exists, value: "التحقق عبر نفاذ" }

  # Body text
  - assert:
      type: text_exists
      value: "A verification request has been sent to your Nafath app"

  # CTA present
  - assert: { type: element_exists, text: "Cancel" }
Reality check on Nafath. The runner drives and validates the app's UI. It cannot approve the real Nafath push in the external Nafath app, and it cannot check the backend (“Validate with backend”, case 7). To automate scenarios A–F (code expired, verification failed, cool-down timer, block message) you need the app pointed at a test/mock backend that returns those states on demand — then each state's copy (the EN/AR strings in your tables) becomes a text_exists assert exactly like above. What is automatable today: navigation, which screen you land on, and every visible string/control in both languages.

10 · Finding an app's real selectors

Easiest — inspect mode (no test file). Launch the screen, then let the engine fetch everything into a bundle you can read:

adb shell monkey -p <package> -c android.intent.category.LAUNCHER 1
py cli.py inspect --label home        # → screens\home\{inventory.md, hierarchy.xml, screenshot.png, observation.json}

screens\home\inventory.md is a table of every element — kind, real resource-id, text, flags, bounds — plus the screen's structural fingerprint. Re-run per screen (--label login, --label cart) to map a multi-screen story. Often you won't need ids at all: use the visible label as the target and let ranking bind it.

Raw alternatives (same data, lower level):

adb -s emulator-5554 shell am start -n <package>/<activity>
adb -s emulator-5554 exec-out uiautomator dump /dev/tty      # prints the hierarchy XML

Or interactively in Python (same layer the runner uses):

py -c "import uiautomator2 as u2; d=u2.connect('emulator-5554'); print(d.dump_hierarchy())"

Look for resource-id="…", text="…", and content-desc="…" on the fields/buttons you act on. The helper script examples\manual_flow.py lets you probe a screen and try selectors before committing them to a YAML.

11 · What it can and can't do

✓ Can install/launch any APK, drive taps/typing/swipes, find controls by id/text/desc/OCR, recover (wait, dismiss keyboard, scroll) before failing, validate visible text (incl. Arabic), the current screen, control presence, and state transitions — and produce screenshot + hierarchy evidence per step.

✗ Can't approve external flows (a real Nafath/OTP push in another app), read SMS OTPs, or check server/database state. It validates the app UI. For backend-dependent scenarios, point the app at a test or mock backend that produces each state, then assert the resulting on-screen copy. Real biometric/CAPTCHA gates are out of scope by design.
